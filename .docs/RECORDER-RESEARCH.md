# 录制功能调研 - RECORDER-RESEARCH.md

## 为什么要做

手工编写用例的成本不可接受。实测：一条 7 步的 BOSS 挑战用例，从走查界面、
裁 9 个锚点素材、到调通，花了一个多小时、十几轮往返，中途还因为
「用页签外观判断当前层」而误判，把角色传送到了错误的层。

按这个成本，几十条用例的规模铺不开。而且这与最初目标相反：
目标是「测一遍、录下来、重复回放」，现在却是「每条用例手工雕」。

## 参考产品：自动按键精灵（com.jshd.auto v9.6.4）

用户已购买会员，在测试云机上作为使用者观察其形态与数据模型。
**只观察外部可见行为，不反编译、不提取其代码。**

### 产品形态

- **悬浮工具栏 / 悬浮球**作为录制与运行的控制入口，不在主界面里操作。
- 任务（Job）按**文件夹**组织：一个游戏一个文件夹，内含十几个独立小任务。
- 每个任务可单独运行，列表项上直接有播放按钮。
- 部分任务带闹钟图标，表示已配置定时触发。

一个真实文件夹（热血封神）里的任务划分，粒度值得参考：

```text
挂机 / 手动挂机 / BOSS盛宴 / 单个地图挂机 / 日常任务-一排 / 日常任务-二排
F整理包裹 / 手动延迟挂机 / 生肖-牛 / 生肖-猪 / 会员挂机 / 一键(总入口)
```

**不是一个大脚本，而是很多个单一职责的小任务**，再由一个「一键」总任务串起来。
「日常任务」还按界面上的行拆成一排/二排。

### 任务的数据模型（任务概览页可见字段）

| 字段 | 观察到的值 | 说明 |
|---|---|---|
| 任务ID | `1424114770858307` | 数字型唯一 ID |
| 动作数量 | `1个` | 该任务的动作条数 |
| **分辨率** | 推荐 `720x1280@2.0`／当前 `720x1280@2.0` | **同时记录分辨率与密度，并与当前设备对比** |
| **关联任务** | `0个` | **任务之间可以关联/串联** |
| 启动类型 | 自行选择 | |
| 定时设置 | 未设置 | 内建定时触发 |
| 远程控制 | 未设置 | |
| 导出任务文件 | `/sdcard/自动按键点击导出` | 导出为 zip |

### 技术线索

- **依赖无障碍服务**：新建、编辑、运行任务都会要求开启，说明点击注入走无障碍。
- **悬浮窗**：录制控制条常驻屏幕。
- **导出文件是加密的**：`.zip` 内单个条目 `job`，压缩方法 99（WinZip AES）、
  加密标志位置 1。厂商刻意保护（其内置脚本交流区在售卖脚本）。
  **不尝试破解**，改由界面观察获取同等信息。

## 对我们设计的直接启发

1. **基线要带密度。** 我们的 `CASE-SCHEMA` 只记了 `baseline.width/height`，
   它还记了 `@2.0`。密度不同会影响素材的物理尺寸，值得补上。
2. **它把「当前值 vs 推荐值」摆在任务首页。** 这正是我们
   `screen.assertCaptureSpace` 想解决的问题，但它是提前告知而非运行时报错，
   体验更好。
3. **任务间关联是内建能力。** 我们 `CASE-SCHEMA` v1 明确不支持用例间引用，
   而真实场景（登录 → 做事）立刻就需要它。这条缺口的优先级要提高。
4. **粒度：多个小任务 + 一个总入口**，而不是一条长用例。
   与我们目前「一条 login-rxfs 包办到底」的做法不同，值得调整。
5. **定时是任务的属性，不是外部调度器的事。** 与我们「常驻脚本 + 进程内循环」
   的方向一致。

## 待确认（需要在设备上开启其无障碍服务后继续）

- 录制时它如何决定「点这里」的判据：只存坐标，还是自动截取锚点图像？
- 若存锚点，锚点区域怎么选（大小、是否避开动态背景）、失败如何提示。
- 如何表达等待：固定延时，还是等某个画面出现。
- 动作类型有哪些（点击/滑动/找图/找色/OCR/条件/循环）。
- 「关联任务」的语义：顺序串联，还是可传参调用。
