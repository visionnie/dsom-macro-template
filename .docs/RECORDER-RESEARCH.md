# 录制功能调研 - RECORDER-RESEARCH.md

## 为什么要做

手工编写用例的成本不可接受。实测：一条 7 步的 BOSS 挑战用例，从走查界面、
裁 9 个锚点素材、到调通，花了一个多小时、十几轮往返，中途还因为
「用页签外观判断当前层」而误判，把角色传送到了错误的层。

按这个成本，几十条用例的规模铺不开。而且这与最初目标相反：
目标是「测一遍、录下来、重复回放」，现在却是「每条用例手工雕」。

## 参考产品：自动按键精灵（com.jshd.auto v9.6.4）

用户已购买会员，在测试云机上作为使用者观察其形态与数据模型。
**只观察外部可见行为，不反编译、不提取其代码。**

### 产品形态

- **悬浮工具栏 / 悬浮球**作为录制与运行的控制入口，不在主界面里操作。
- 任务（Job）按**文件夹**组织：一个游戏一个文件夹，内含十几个独立小任务。
- 每个任务可单独运行，列表项上直接有播放按钮。
- 部分任务带闹钟图标，表示已配置定时触发。

一个真实文件夹（热血封神）里的任务划分，粒度值得参考：

```text
挂机 / 手动挂机 / BOSS盛宴 / 单个地图挂机 / 日常任务-一排 / 日常任务-二排
F整理包裹 / 手动延迟挂机 / 生肖-牛 / 生肖-猪 / 会员挂机 / 一键(总入口)
```

**不是一个大脚本，而是很多个单一职责的小任务**，再由一个「一键」总任务串起来。
「日常任务」还按界面上的行拆成一排/二排。

| **关联任务** | `0个` | **任务之间可以关联/串联** |

### 技术线索

- **依赖无障碍服务**：新建、编辑、运行任务都会要求开启，说明点击注入走无障碍。
- **悬浮窗**：录制控制条常驻屏幕。
- **导出文件是加密的**：`.zip` 内单个条目 `job`，压缩方法 99（WinZip AES）、
  加密标志位置 1。厂商刻意保护（其内置脚本交流区在售卖脚本）。
  **不尝试破解**，改由界面观察获取同等信息。

## 对我们设计的直接启发

1. **基线要带密度。** 我们的 `CASE-SCHEMA` 只记了 `baseline.width/height`，
   它还记了 `@2.0`。密度不同会影响素材的物理尺寸，值得补上。
2. **它把「当前值 vs 推荐值」摆在任务首页。** 这正是我们
   `screen.assertCaptureSpace` 想解决的问题，但它是提前告知而非运行时报错，
   体验更好。
3. **任务间关联是内建能力。** 我们 `CASE-SCHEMA` v1 明确不支持用例间引用，
   而真实场景（登录 → 做事）立刻就需要它。这条缺口的优先级要提高。
4. **粒度：多个小任务 + 一个总入口**，而不是一条长用例。
   与我们目前「一条 login-rxfs 包办到底」的做法不同，值得调整。
5. **定时是任务的属性，不是外部调度器的事。** 与我们「常驻脚本 + 进程内循环」
   的方向一致。

## 由用户讲解补齐的设计模型（2026-09-03）

以下由已购买会员并长期使用该工具的项目所有者讲解，是自购正版的使用经验，
不是逆向所得。目的是学习设计意图，指导我们自己独立实现。

### 任务的三种粒度

- **原子任务**：具体动作序列（如「1010领取奖励」有 9 个节点）
- **子任务**：被别的任务复用的原子任务（如「F异常处理」「G福利」）
- **总入口**：串联很多子任务（如「一键热血封神」）

对应到界面上的「关联任务：12 个」——`1010领取奖励` 关联了 12 个子任务。

### 节点的三种角色（关键发现）

每个节点可以是三种之一，这直接决定了 schema 需要一个 `type` 字段：

1. **行为节点**：具体动作（点击、滑动、OCR 等）
2. **任务引用节点**：直接指向另一个任务并执行完它（如引用「F异常处理」）
3. **空节点（占位/汇合）**：不做事，只用作跳转目标或占位

配合每个节点的 `执行成功后 / 执行失败后` 两个跳转字段，实际是**在做流程图**：

```text
1. F异常处理  (空节点)  成功 → 执行[F异常处理]   失败 → 下一步
2. 回城       (空节点)  ...
3. G经脉      (空节点)  ...
...
9. 挂机
```

节点的名字（如「F异常处理」）就是节点标签，被前面节点的「执行成功后」引用，
形成**类似 goto 的流程控制**，而不是硬编码的顺序执行。这解释了它为什么能
把复杂逻辑组织得清晰——它不是链，是**带跳转的节点图**。

### 定时是任务自身属性

界面上的闹钟图标 = 该任务开了定时。相关设置：

- **开启定时** + **每日定时** + **重复方式**（按周几 / 按工作日）
- **强制执行**：定时到时若有别的流程在跑，先关掉再执行本任务
- **解锁流程**：单独配一个专门用来解锁手机屏幕的任务，被定时任务在触发时先调用

后两条对我们很关键——**它把「无人值守的现实问题」当一等公民对待**：
既处理任务冲突，也处理锁屏。我们的 HANDOFF 里「常驻脚本」还只考虑到了
"授权不掉线"，没想到锁屏和冲突。

### 动作类型（图 9 的分类）

| 分类 | 具体动作 |
|---|---|
| 普通点击 | 点击 / 连续点击 / 区域点击 / 区域随机点击 / 长按 / 随机动作组 |
| **匹配点击** | 点击图片 / 点击文字 / 点击节点·控件 / 点击颜色 / **AI 特征点击** |
| 文本/网络 | 输入文字 / 文本提取·复制 / 变量操控 / HTTP 请求 / 调用 AI 大模型 / 读写 Excel / 分享文件 |
| **逻辑控制** | **空节点** / **控制流程** / 全局监听 / 倒计时 / 分流跳转 |
| 手势滑动 | 单指滑动 / 多指手势 / 定长滑动 / 匹配拖拽 / 滚动行·页 |
| 手机快捷键 | ...（未完全展开） |

**关键分类：普通点击 vs 匹配点击**——它明确把"死坐标点击"和"找到再点"分开，
分类本身就在教用户区别使用。这也正是我今天 BOSS 用例踩坑之处
（页签靠坐标定位失效，靠找图定位才稳）。

### 点击动作的参数（图 8）

以「点击」为例，参数结构：

| 字段 | 值 |
|---|---|
| 运行等待 | 固定延时 1000ms（还有其他类型下拉可选） |
| 运行条件 | 未设置 |
| 动作类型 | 点击 |
| **坐标类型** | **固定坐标 (75.0%, 20.13%)** ← **归一化百分比，不是绝对像素** |
| 随机微调 | 未设置（用于反检测） |
| 按下时间 | 107ms（大于 500ms 就是长按） |
| 执行成功后 | 下一步 |
| 执行失败后 | 下一步 |
| 节点名称 | 福利 |

**几点直接抄用**：

- **坐标存 % 而不是像素**，与我们 `case-geometry` 归一化坐标一致，方向对了
- **按下时间可配**，与我们改 `click()` 为 `press()` 的修复呼应
- **随机微调**是反检测手段，某些游戏会检测机械化点击
- **每个节点独立可配"成功/失败跳转"**，节点即流程图节点

## 命名约定：用任务名前缀标定时时刻

观察到用户的任务命名模式：`0930上午-金猪` / `1010领取奖励` / `1100押镖`
/ `1400跨服竞技` / `2000沙巴克`。**前 4 位是 HHMM 触发时刻**。

这是纯粹的命名约定，不需要工具支持——但让人一眼看出任务表的时间分布，
比在编辑页里点开每个任务看定时设置快得多。我们的实现应鼓励这种约定，
文档里给出示例。

## 我们要做的差异化

用户放弃使用该工具、要求自研，核心原因是**授权模式**：
一账号一设备，多测试机场景无法接受。

因此我们的实现除功能对齐外，必须坚持：

- **任务文件为明文 JSON**，用户随时可读、可改、可备份、可 diff
- **多设备免费**，同一份任务可推到 N 台云机同时执行，不联网校验
- **导出即所得**，不加密、不绑账号
- **能被 git 管理**，任务是代码，用户是所有者

## 我们实际要做的动作类型（由项目所有者确认）

对方产品支持的动作分类很多，但**用户长期实际使用的只有三种**，其他一概不做：

1. **空节点**（占位/汇合，供「关联任务」引用；也是节点跳转的目标）
2. **点击**（普通点击，参数=归一化坐标、按下时间、成功/失败跳转）
3. **点击图片**（匹配点击，锚点=用户手工框的一小块区域，运行时找图定位后点中心）

对应到我们的实现，这就是 MVP 的边界。其他动作类型（区域随机点击、随机微调、
控制流程、AI 特征点击、HTTP 请求、读写 Excel、多指手势……）**均不做**，
避免陷入功能对齐的无底洞。

### 录制器最关键的问题：锚点从哪来？

**由用户手工框选一小块区域**，不做自动截取。

这是刻意选择：自动挑锚点是脆的，今天 BOSS 用例就吃过亏——把动态背景框进
模板后平均像素差 26 完全匹配不上。让人来框，锚点质量由用户负责，工具不猜。
用户比工具懂"这个界面里什么是稳定的"。

对录制器 UI 的直接影响：录制过程中点击「点击图片」类型时，界面必须暂停并
提供**在当前截图上拉框**的能力，框完再继续录下一步。
